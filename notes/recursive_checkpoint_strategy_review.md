# Recursive Checkpoint Strategy：逻辑与实现审查

> 审查日期：2026-09-16。对应 [递归检查点策略](recursive_checkpoint_strategy.md)，分析其数学推导、实现行为与适用范围。测试结果对应审查当日的版本。

## 审查结论

递归二分 checkpoint 是有价值的时间–空间折中：在固定 block 形状、忽略框架元数据等开销的理想模型下，可用约 $O(r+x\log N)$ 的激活存储，换取 $O(N\log N)$ 的 block 级前向计算。但原文不能据此声称“忽略计算成本时全局最省内存”，也没有正确证明 $m^*=e$。

参考实现能正确传播梯度，已通过 36 组 toy 检查与 3 组仓库 TransformerBlock 检查。不过代码与文字描述的嵌套深度不一致，空列表没有终止条件，精确重算次数受 early-stop 影响。原文声称的 $4x+r$ 峰值没有得到实际 GPU 内存测量验证。

## 一、优化目标与最优性

### 1. “忽略计算成本”与“平衡二叉最优”不是同一个问题

原文只优化了均匀、平衡的 $m$ 叉分割，不能排除不平衡递归或其他重计算调度。

[Gradient Checkpointing](gradient_checkpointing.md) 的 (a) 给出了另一种方案：每次把前 $N-1$ 个 block 包进 checkpoint，最后一个 block 直接计算，再在前缀内部重复相同策略。这正是需要拿来比较的反例，而不是可以忽略的另一个实现。

在只统计激活 tensor storage、保留原始输入并按需重算的理想模型里，该前缀策略可以反复从同一个原始输入恢复当前所需的前缀，只在当前末端保留一个 block 量级的 residuals。因此可以达到 $O(r+x)$ 的激活空间，而付出 $O(N^2)$ 的 block 级前向计算。在固定 $r,x$ 时，前者对 $N$ 为 $O(1)$。

前缀递归策略的测试结果：关闭 early-stop 后，$N=1,3,8,32$ 的 block 前向调用数分别为 $1,6,36,528$，符合原笔记的 $N(N+1)/2$；输出、输入梯度、参数梯度与普通计算一致。这是计算次数和梯度的验证，不是 GPU 峰值空间实测。

因此，原文最后一句应收窄为：**平衡二叉是节省激活内存、同时控制重算成本的一种策略；不能把它当成“完全不计计算成本”条件下的全局内存最优方案。**

这里的常数空间不包含随层数增长的模型参数、参数梯度、Python 递归栈、autograd 图、checkpoint 元数据和 RNG 状态。特别是 `use_reentrant=False` 保留图结构，因此不能把“激活 storage 是常数阶”写成“整个程序内存是常数阶”。

### 2. $m^*=e$ 的推导丢掉了决定最优点的项

先暂时接受原文的理想化目标，并略去与 $m,d$ 无关的 $x$：

$$
f(m,d)=d(m-1)x+\frac{Nr}{m^d},\qquad A=\frac{Nr}{x}.
$$

固定 $d>0$、把 $m$ 暂时当连续变量时，原文求得 $m^*=A^{1/(d+1)}$ 这一步是对的。但代回后的精确式是：

$$
f(d)=x\left[(d+1)A^{1/(d+1)}-d\right].
$$

原文存在两个问题：

1. Step 1 的“代回得”中，最后一项写成了 $(Nr)^{1/(d+1)}x^{1/(d+1)}$；正确的 $x$ 指数应为 $d/(d+1)$。
2. 随后把 $-dx$ 丢掉，改为优化 $(d+1)xA^{1/(d+1)}$。虽然对这个近似函数能精确求得 $t^*=\ln A$，但它不是原函数的精确解。

关键是该近似在候选最优点附近不成立。原文依据 $A\gg1$ 推断 $A^{1/(d+1)}\gg1$，当 $d$ 也随 $A$ 增大时，这个推断不成立；它自己求出的候选点恰好给出 $A^{1/(d+1)}=e$。此时不能忽略 $(m-1)$ 中的 $-1$。

可直接检查精确函数。令 $t=d+1$、$a=\ln A>0$：

$$
f(t)=x\left[te^{a/t}-t+1\right],
\qquad
\frac{df}{dt}=x\left[e^{a/t}\left(1-\frac at\right)-1\right].
$$

对于 $z=a/t>0$，$e^z(1-z)-1<0$，因此这个无约束代回函数没有原文宣称的有限内部最优点。实际最优解要由合法分支数、整数深度和叶子段长等约束决定。

### 3. 必须加上“每个叶子至少一个 block”的约束

合法的均匀划分至少要求：

$$
m\ge2,\qquad d\in\mathbb Z_{\ge0},\qquad m^d\le N.
$$

若还要求每个叶子长度完全相等，则需要相应的整除条件。原文前面设 $N=m^d$，后面又用 $N=8,m=2,d=2$，这两处定义冲突。应定义叶子段长 $L=N/m^d\ge1$，切到底才满足 $N=m^d$。

例如 $N=32,r/x=45,d=5$ 时，无约束公式给出 $m^*=1440^{1/6}\approx3.36$，但合法分支数必须满足 $m\le32^{1/5}=2$。候选点超出了可行域。

### 4. 固定二叉时，不应套用“同时优化分支数”的 $d^*$

在原文理想模型中，固定 $m=2$：

$$
M(d)=(1+d)x+\frac{Nr}{2^d},
$$

相邻合法深度之间的差为：

$$
M(d+1)-M(d)=x-\frac{Nr}{2^{d+1}}.
$$

只要还能完整二分且 $r>x$，右侧为负，因此在这个模型的二叉族内切到底更省内存。对 $N=32,r/x=45$，$d=1,2,3,4,5$ 的 $M(d)/x$ 分别为 $722,363,184,95,51$。

原文“大到某个 $N$ 后，就存在不切到底的中间最优深度”的判断，是把可变 $m$ 的近似公式套到了固定 $m=2$ 的问题上。$N=32$ 切到底这个局部结论可以成立，但给出的推理依据不成立。

### 5. $N=64$ 的对比表比较错了系数

原文公式的 checkpoint 系数为 $1+(m-1)d$，验证表却改成 $md$。这会改变排序。

当 $N=m^d$、叶子均为一个 block 时，应比较：

| 分支数 $m$ | 深度 $d$ | checkpoint 系数 $1+(m-1)d$ |
|---|---|---|
| 2 | 6 | 7 |
| 4 | 3 | 10 |
| 8 | 2 | 15 |

$m=3$ 时 $\log_3 64\approx3.79$ 不是合法整数深度，必须先说明非均匀叶子或补齐规则，不能当成一棵真实完整树的验证。

如果仅在“切到底的均匀树”这个理想模型中作连续比较，相关项为 $(m-1)/\ln m$，其在 $m>1$ 时单调递增。因此该受限模型倾向最小合法整数分支数 2；这并不需要、也不支持 $m^*=e$ 的论证，更不能扩展为所有调度中的全局最优。

## 二、内存计数与 checkpoint 语义

### 1. $3x+2r$、$4x+r$ 应标为模型估计

这些式子适合解释“边界激活 + 当前重算区域”的权衡，但需要额外假设，不能直接等同于 PyTorch/CUDA 的实测峰值：

* $r$ 必须与另外计入的 checkpoint 输入 storage 不重叠；“全部中间激活”可能已经包含输入或其 view，否则会重复计数。
* 数值相等的两个 tensor 不代表共享内存；不同 tensor 对象也可能共享同一个 storage。应以**同时存活的唯一底层 storage**为依据，而不是按数值或 Python 对象数量简单去重。
* 原始输入、最终输出、激活梯度、算子临时工作区、参数梯度等有各自的生命周期。Forward 没有长期保存 residuals，也仍需要临时 tensor 来执行算子。
* 初始输入若仍被调用者的 `x` 引用，checkpoint 释放自身引用不意味着它的内存释放。表格最后的“0”只能理解为该抽象模型不再由 checkpoint 持有的部分。
* 非均匀 block 或非均匀分段时，峰值未必在最深、最右侧的叶子；必须比较实际时间线。

因此“Peak 在 backward”不是无条件定理，尤其当 forward 算子有很大的临时工作区时。

### 2. 非重入模式的内层输入由外层管理，不是等作用域结束后统一释放

本机 PyTorch 2.11.0 的 `torch/utils/checkpoint.py` 在 `NOTE [ Nestable Checkpoint ]` 中明确区分：内部 saved tensors 由最内层 checkpoint 管理；内层 checkpoint 的输入则作为父 checkpoint 的 saved tensors 处理。

在 `use_reentrant=False` 下，外层保存钩子通常使内层输入不被作为普通 tensor 长期保留；仍可能有执行所需的临时引用。因而原文 F5/F8、F13/F16 的“先保存，等离开 cpA/cpD 才强制释放”不是精确的框架事件记录。

外层重算为内层重算提供所需输入这个方向是对的。但 non-reentrant 的 early-stop 会在所需 saved tensors 已重建时提前停止，不要求执行完整个区域；重算缓存中的 tensor 也会在被取用时清除，而不是统一等外层 backward 完成。因此这套 F/B 表应标记为抽象示意，而不是已验证的运行 trace。

源码依据：[PyTorch 2.11.0 checkpoint 源码](https://github.com/pytorch/pytorch/blob/v2.11.0/torch/utils/checkpoint.py)。

### 3. `use_reentrant=True` 不等于“多复制一份输入”

原文关于 `True` 的两项判断应订正：

* 其保存/分离输入的过程不意味着克隆底层 tensor 数据；`detach` 与原 tensor 共享 storage。“False 能去重，而 True 必定多一份数据”没有依据。
* PyTorch 2.11 文档推荐显式使用 `False`，但仍描述并支持 `True`。不能把“不显式传入参数的旧用法受到弃用警告”解释为 `True` 模式本身已经废弃。

选择 `False` 的实际理由包括 autograd 支持和 early-stop 等行为差异。[PyTorch checkpoint 文档](https://docs.pytorch.org/docs/2.11/checkpoint.html)

### 4. 深度与根节点的口径不一致

原文一般公式提到“最外层包一个根 checkpoint”，但 $N=8,d=2$ 的图只有并列的 cpA/cpD，参考代码的 `run(blocks,x)` 也没有包一个全局根。

公式里的“1 个原始边界”可以作为计数基点，但不必对应一个实际的根 checkpoint 调用。应把“划分深度”“实际 checkpoint 嵌套层数”“是否有全局根包装”分别定义；额外根包装可能增加重算，不一定新增一份唯一输入 storage。

### 5. $r/x$ 数值与已有测量方法

输入的 $80\text{ MiB}$ 计算正确（float32）。但 $3.6\text{ GiB}/80\text{ MiB}=46.08$，已有日志的 $3651.31\text{ MiB}/80\text{ MiB}\approx45.64$，所以 45 只能作为粗略近似。

[checkpointing&recomputation.py](../cs336_systems/checkpointing%26recomputation.py) 的 `pack_hook` 累计的是每次保存时的 `numel × element_size`，不是同时存活的唯一 activation storage：相同 storage 多次保存可能重复累计；参数的转置/view 也未必是 `torch.nn.Parameter` 对象，可能漏过参数过滤。因此日志不足以精确证明 $r$ 或训练峰值；也不能将 compiled 与 eager 的保存行为直接混为一谈。

## 三、参考实现的实际检查

### 1. 非空列表的输出和梯度：通过

测试对象为参考实现中的 `C` 和 `run`；测试环境提供所需的类型定义、输入和模块实例。

环境：项目 `.venv`，PyTorch 2.11.0，CPU，`torch.cuda.is_available() == False`。

| 检查 | 覆盖范围 | 结果 |
|---|---|---|
| toy 输出、输入梯度、参数梯度 | $N=1,2,3,8,9,32$；early-stop 开/关；输入求梯度/不求梯度；含 dropout 的固定种子对照 | 36 组通过 |
| 仓库 TransformerBlock | $N=1,3,8$，输入 `(2,8,16)`，2 heads，FFN 32，RoPE | 3 组通过 |
| 前缀递归策略 | $N=1,3,8,32$，完整重算模式 | 4 组梯度及调用数检查通过 |
| 空 `blocks` | 原样调用 `run([], x)` | `RecursionError` |
| 独立执行参考代码 | 未补任何上下文 | `NameError: name 'Block' is not defined` |

toy 使用 float64，断言容差为 `rtol=1e-10, atol=1e-12`；Transformer 对照使用 float32 和 `torch.testing.assert_close` 默认容差。非 2 的幂的正长度在这些检查中没有梯度错误，只是不再满足完全均匀树的精确公式。

### 2. 叶子重复 checkpoint：结构与正文差一层

观察长度为 2 的调用：父层先调用 `C(lambda x: run(left,x),x)`，而 `run` 收到长度为 1 的列表后，又调用 `C(lambda x: blocks[0](x),x)`。

这相当于父层已包住单 block 的执行路径，叶子内部又包装一次。$N=8$ 时，一个 block 的路径上实际有 4 个 checkpoint 包装，原文却按 3 层计算。该问题未造成测试中的梯度错误，但会增加调度/元数据开销，在完整重算模式下还会增加一次整网等价前向。

需要核对的修改方向是：**单 block 路径是否只应保留一次包装，以及 $N=1$ 的单独调用应采用什么行为**。这属于实现与定义的一致性问题，不能只改最后一行计算次数来掩盖。

### 3. “4 次 forward”没有被原代码验证

对原代码加入 block 入口计数，$N=8$ 的结果如下（包含初始 forward）：

| 模式 | B1–B8 的累计进入次数 | 总数 |
|---|---|---|
| 默认 non-reentrant early-stop | `[4,3,3,2,4,3,3,2]` | 24 |
| 关闭 early-stop，完整重算 | `[5,5,5,5,5,5,5,5]` | 40 |

默认模式下有些调用会在内部算子之后提前终止，因此入口计数不等于完整 block 的 FLOPs。不能把 24 次入口简单叫作“3 次完整网络前向”。关闭 early-stop 后，40 次完整 block 调用对应 5 次整网等价前向，而不是原文写的 4 次。

原文的 $F(d)=d+1$ 可以描述一个每层都完整重算、深度定义一致的理想模型；不能不加区分地当成当前 non-reentrant 实现的精确运行次数。

### 4. 空列表与缺少运行上下文

`len(blocks)==1` 是唯一终止条件。长度为 0 时 `mid=0`，`left` 仍为空，递归不会缩小问题。因此需要明确空列表是非法输入，还是恒等映射，并按该约定处理。

`Block`、`Tensor`、`blocks`、`x` 在参考代码片段中没有定义。在本机 Python 3.13 上，独立执行首先在类型注解处报 `Block` 未定义。这说明它是依赖上下文的代码片段，不是可直接运行的完整脚本。

`left/right` 来自每次递归自己的局部作用域，在当前非循环写法中没有发现典型的循环变量晚绑定问题。没有必要把所有 lambda 都判成 bug。

### 5. 还需明确的执行约束

* 重算前后 block 的数学行为、参数和相关状态必须一致；如果 forward 修改计数器、缓存或其他持久状态，重复执行可能改变训练行为。测试中的计数器仅用于观测，不参与输出。
* 默认 RNG 保存机制在 CPU dropout 对照中有效；没有验证跨设备移动、自定义随机源、混合精度或 GPU dropout。
* 若这些 block 用于实际模型训练，还应确认它们由外部 `nn.Module` 正确注册、被 optimizer 收集。当前函数接收 Python 列表本身不是梯度错误，但也不负责模块注册。

## 四、可保留的结论与验证边界

可以保留“分段重算降低长期保存的激活”“共享 storage 不应重复计数”“平衡递归提供对数级边界存储”这些核心直觉；应删除或加限定的，是精确最优常数、对实现的未经测量的峰值断言，以及全局最优性。

在固定 $x,r$、均匀 block、理想平衡二叉树中，可用如下量级描述：

$$
M_{\mathrm{activation}}=O(r+x\log N),
\qquad
C_{\mathrm{forward}}=O(N\log N).
$$

这里总 block 前向计算为 $O(N\log N)$，相对于普通整网前向的**倍数**才是 $O(\log N)$。常规 block backward 总工作量另为 $O(N)$；没有把 FLOPs、函数入口次数和整网等价遍历次数混为一谈。

尚未测量 CUDA 峰值、XL 配置、`torch.compile` 和真实训练吞吐，因此不声称已验证 $4x+r$ 或某个 GiB 级峰值。后续若测量，应记录完整 forward+backward 的分配峰值，区分 allocated/reserved，排除固定参数和优化器状态，并控制外部 tensor 引用与 storage 去重口径。
