## 观察到的现象

### 现象 1：速度显著提升

- **小序列** (n=256)：加速 1.0–1.8×
- **中序列** (n=1024)：加速 1.4–2.0×
- **大序列** (n≥4096)：加速 **2.5–3.5×**

### 现象 2：Backward 加速比更高

- Forward 平均加速：~2.3×
- Backward 平均加速：**~2.8×**

### 现象 3：内存几乎不变

- 差异 < 0.2%
- OOM 点不变 (n=16384)

---

## 分析：为什么速度有提升

### 1. Kernel Fusion (算子融合)

**Uncompiled (Eager Mode)**：

```text
Q @ K^T → div sqrt(d) → mask → softmax → @ V
   ↓          ↓          ↓        ↓       ↓
kernel1   kernel2    kernel3  kernel4  kernel5
   ↑          ↑          ↑        ↑       ↑
读写全局内存，每个 kernel 有 launch 开销
```

**Compiled**：

```text
Q @ K^T → div → mask → softmax → @ V
   └─────────────┴───────────────┘
             单个 fused kernel
             中间结果在寄存器/共享内存
```

**收益**：

- 减少 GPU kernel launch 开销（每个 kernel ~5–10μs）
- 减少全局内存读写次数
- 提高缓存利用率

### 2. Python 开销消除

**Uncompiled**：

```python
for _ in range(100):
    out = scaled_dot_product_attention(Q, K, V)
    # 每次：Python 解释器 → C++ API → GPU kernel
```

**Compiled**：

```python
for _ in range(100):
    out = compiled_fn(Q, K, V)
    # 第一次后：直接执行预编译的 GPU kernel
```

### 3. 内存访问优化

- **Eager**：每个算子都读写全局内存
- **Compiled**：中间结果保留在寄存器/共享内存

### 4. 为什么大序列收益更大

| 因素 | 小序列 | 大序列 |
|------|--------|--------|
| Python overhead | 占比高 (~30%) | 占比低 (~5%) |
| Kernel launch 次数 | 少 | 多，融合收益大 |
| 内存带宽 | 不是瓶颈 | 是瓶颈，优化收益大 |

---

## 结论

| 指标 | 结果 | 原因 |
|------|------|------|
| **速度提升** | 2–3.5× | Kernel fusion + Python 开销消除 + 内存访问优化 |
| **内存不变** | < 0.2% 差异 | 算法复杂度 O(n²) 未改变 |
| **OOM 点不变** | n=16384 | 内存瓶颈是算法本质 |

**关键洞察**：`torch.compile` 是**实现层面的优化**，不改变**算法层面的复杂度**。要突破内存瓶颈，需要 FlashAttention-2 的算法创新。

## E2E Transformer 对比 (Part b)

### 实验配置

- batch_size: 4
- context_length: 512
- 设备：MPS (Apple Silicon)
- 模型：BasicsTransformerLM

### 结果对比

| 模型 | Mode | Uncompiled (s) | Compiled (s) | Speedup |
|------|------|----------------|--------------|---------|
| **Small** (768d, 12L) | forward | 0.1043 | 0.0625 | **1.67×** |
| **Small** (768d, 12L) | backward | 0.3157 | 0.2004 | **1.58×** |
| **Small** (768d, 12L) | optimizer | 0.3540 | 0.2396 | **1.48×** |
| **Medium** (1024d, 24L) | forward | 0.3100 | 0.1982 | **1.56×** |
| **Medium** (1024d, 24L) | backward | 0.9940 | 0.6387 | **1.56×** |
| **Medium** (1024d, 24L) | optimizer | 1.2385 | 0.8323 | **1.49×** |
| **Large** (1280d, 36L) | forward | 0.6892 | 0.4528 | **1.52×** |
| **Large** (1280d, 36L) | backward | 2.3455 | 1.6881 | **1.39×** |
| **Large** (1280d, 36L) | optimizer | 2.6765 | 3.1461 | **0.85×** ❌ |

### 关键发现

#### 1. E2E 加速比低于 Attention-only

| 场景 | 加速比 |
|------|--------|
| Attention only (n=8192) | 2.5–3.5× |
| E2E Transformer | 1.4–1.7× |

**原因**：E2E 中有更多非 attention 操作 (embedding, FFN, layer norm)，这些操作的编译优化空间有限。

#### 2. Large 模型 Optimizer 异常变慢

- Uncompiled: 2.68s
- Compiled: 3.15s
- **Compiled 更慢！**

**可能原因**：

- AdamW optimizer 的 Python 控制流导致 graph break
- 参数更新逻辑无法被编译优化
- 内存分配模式改变 (compiled 版本可能使用不同的内存布局)

#### 3. 标准差分析

| 模型 | Mode | Uncompiled σ | Compiled σ | 稳定性 |
|------|------|--------------|------------|--------|
| Small | forward | 0.0004 | 0.0002 | Compiled 更稳定 ✅ |
| Small | backward | 0.0012 | 0.0004 | Compiled 更稳定 ✅ |
| Medium | backward | 0.0405 | 0.0362 | Compiled 略稳定 |
| Large | backward | 0.0690 | 0.1630 | Uncompiled 更稳定 ❌ |

**观察**：Compiled 版本在大部分情况下更稳定，但 Large 模型的 backward 波动更大。

### E2E 结论

| 指标 | 结果 | 说明 |
|------|------|------|
| Forward 加速 | 1.5–1.7× | 有效，但低于 attention-only |
| Backward 加速 | 1.4–1.6× | 有效，但低于 attention-only |
| Optimizer 加速 | 1.5× (Small/Medium) | Large 模型异常变慢 |
| 内存变化 | 未测量 | 预期与 attention-only 类似（不变） |

**关键洞察**：`torch.compile` 在 E2E 场景收益有限，因为：

1. 非 attention 操作 (FFN, LayerNorm) 本身已经高效
2. Optimizer 的 Python 逻辑难以编译优化
3. 模型越大，编译优化的相对收益越小（绝对时间仍减少）
